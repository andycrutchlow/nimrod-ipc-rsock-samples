# Nimrod benchmark client timeout investigation

Current samples resolve **Nimrod IPC 4.3.1 from Maven Central**. This note preserves the archived pre-release timeout investigation; its version references identify the inspected binary. See [binary provenance](../BENCHMARKS.md#release-and-benchmark-binary-provenance) and [release validation](release-validation.md).

The inspected 4.3.1-SNAPSHOT `RemoteServerService.executeRmiMethod` borrows a `RSocketRequester` from Commons Pool, calls `retrieveMono(responseClass).block()` without a duration and returns the requester in `finally`. Pool borrowing also has no explicit wait limit in the current factory configuration. Keepalive/reconnect options govern connection detection/recovery; they are not a request deadline. The benchmark uses the generated proxy unchanged.

The annotation processor can add a server-side `Mono.timeout` from interface `timeoutMs`. That bounds the server reactive response, not a client waiting on an unreachable or silent peer, and cannot establish cancellation of arbitrary application work. The benchmark does not repurpose it as proof of a native client timeout.

The runner enforces an outer wall budget by tracking each worker's active-call start and interrupting it when the shared deadline expires. In the exercised Reactor blocking path, interruption raises `ReactiveException(InterruptedException)` and unwinds through Nimrod's `finally`; the local call stops. A stalled-server integration check uses a 200 ms client budget and a 1,500 ms server delay. Its readiness call is counted as timed out, no replacement request is sent and the client exits nonzero with an invalid performance summary. The server is stopped by the supervisor afterward.

**This is a benchmark deadline/abort mechanism, not an added native Nimrod RPC timeout.** Java interruption is cooperative. Returning the requester does not prove the remote invocation was cancelled or rolled back, and a network interruption may differ from the exercised delay. Do not continue generating requests after such a timeout or automatically retry. Timeout measurements are not advertised as semantically equivalent to gRPC/Dubbo native deadlines.

The unit checks cover both an interruptible stall and a deliberately uninterruptible call. The latter remains unresolved after a finite drain, is reported as such and cannot prevent the runner returning. Workers are daemon threads, and finite benchmark clients use explicit process exit. The Python process-group supervisor supplies a second bound: at most 35 seconds for server bind, a configured warmup/measurement/drain plus 20 seconds for the client, and bounded TERM/KILL shutdown. Binding readiness is followed by a separately validated application RPC before warmup.

The default call budget is five seconds and monitor resolution is approximately five milliseconds plus scheduling delay. Default drain is 30 seconds; short fault checks use two seconds. CLI durations, payloads, concurrency, timeout and drain have validated bounds. A timeout, unfinished call, invalid reply or recorder failure invalidates the performance run. Counts/diagnostics are still retained; unresolved calls may also be counted as timed out, so unresolved is a subset/status, not an additional independent attempt outcome.

No Nimrod library source has been edited for this implementation. A stronger native deadline would require a separately approved library change covering both pool wait and reactive response wait, requester lifecycle, cancellation/reuse and transport/server-side semantics. It is not necessary to make these benchmark processes finite, but remains a limitation for comparing native timeout behavior under arbitrary faults.
